# 软件系统非功能规格说明书：课码 (CodeClass)

非功能需求（Non-functional Requirements）定义了系统的质量属性。本项目需满足以下核心指标：

## 1. 性能需求 (Performance)
* **NFR-P1（响应时间）**：学生提交代码后，简单逻辑错误（如语法错误）的批改反馈需在 **3秒内** 返回；涉及大模型深度分析的复杂逻辑错误，反馈时间应控制在 **15秒内**。
* **NFR-P2（并发能力）**：系统需支持至少 **200名** 学生同时在线并提交作业，此时 API 响应延迟不得超过 5 秒。
* **NFR-P3（缓存机制）**：使用 Redis 缓存常见报错信息和知识图谱热点节点，缓存命中率需达到 **70%** 以上。

## 2. 可靠性与可用性 (Reliability & Availability)
* **NFR-R1（系统可用性）**：系统需保证在作业提交截止日前夜的高峰期，可用性达到 **99.9%**。
* **NFR-R2（容错处理）**：当大模型 API 服务宕机或超时时，系统需降级处理（例如返回基础代码运行报错日志），而不是直接崩溃。
* **NFR-R3（沙箱隔离）**：学生提交的恶意代码或死循环代码，必须在安全的 Docker 容器沙箱中运行，严禁影响服务器宿主机。

## 3. 安全性 (Security)
* **NFR-S1（数据保护）**：学生的个人信息、提交的代码数据必须加密存储，严禁外泄或用于训练公共模型。
* **NFR-S2（权限控制）**：严格的基于角色的访问控制（RBAC），学生不能查看其他同学的代码与反馈，不能修改作业要求。

## 4. 可维护性与扩展性 (Maintainability & Extensibility)
* **NFR-M1（代码规范）**：后端采用 Django 框架，代码需遵循 PEP 8 规范，核心模块需有完整的单元测试（覆盖率 > 80%）。
* **NFR-M2（模块解耦）**：代码解析引擎、大模型接口、业务逻辑需解耦设计，未来支持扩展 Java、C++ 等语言时，无需重构核心架构。

## 5. 易用性 (Usability)
* **NFR-U1（用户界面）**：网页端界面需简洁友好，错误提示需用高亮颜色标出具体代码行。
* **NFR-U2（兼容性）**：支持主流现代浏览器（Chrome, Edge, Safari 等）访问，且适配移动端查看基本反馈信息。
